# SchoolVerse — Module 4: Student & Parent Management

Source of truth: `../School_ERP_Module_04_Student_Parent_Management_PRD_v2.1_Functional_Parity_UX_Enhanced.pdf` (+ the Epic brief)
Depends on: Module 1 (School & Locations), Module 2 (Academic Structure & Sessions), Module 3 (Faculty & Staff, and the shared identity layer). Next modules: Timetable, Attendance, Fees (they consume the Student context built here).
Visual reference: same Quill theme and SchoolVerse accents as Modules 1–3.

**Goal:** one canonical Student per child and one canonical Guardian per adult, linked through effective-dated relationships. A Student is enrolled per Session into a Class Offering, placed in a Section with a Roll Number, and given Subjects (Module 2 IDs only). Parents get controlled, child-specific portal access through the same identity layer Module 3 built. **No second identity stack, no competing Student or Parent masters.**

**Principles:** (1) Student ≠ Enrollment ≠ Section Assignment: history is never overwritten. (2) Parent access is decided on the server from the chain *user → guardian person → active relationship → capability → student → tenant*, never from a `studentId` the browser sends. (3) The five UX principles (Zero Re-entry, Exception First, Configure Once, Stay in Context, System Suggests / Human Decides) shape the APIs too: the server derives, recommends and isolates exceptions so the UI doesn't have to.

## 0. Architecture decisions (locked before Part 1)

| Decision | Choice | Why |
|---|---|---|
| Reuse Modules 1–3 | Same stack, `tenantScope` plugin, `recordAudit`, `withTransaction`, `requirePermission`, error catalog, `@shared` contract, dependency registries, `academicService`, `masterService`, `platform/identity` (account tokens, notifier, private storage, file checks, crypto, security events, rate limits, CSV escaping) | Isolation, audit, RBAC and secure files come for free |
| Code location | Student domain in `backend/src/modules/students/`. Frontend `features/students/` (admin), `features/parent/` (portal), `features/faculty-students/` (class lists) | Downstream modules import `studentService` only |
| People reuse | The `people` model moves from `modules/staff/` to `platform/identity/people/` (pure move, re-exported from `staff` so Module 3 imports keep working). Students and Guardians are `people` rows. One person can be a Guardian of many Students, and can also be an employee | PRD §4: one shared people master |
| Entity separation | `people` → `student_profiles` (school-specific state) → `student_admissions` (permanent admission identity) → `student_academic_enrollments` (per Session) → `student_section_assignments` + `student_subject_enrollments`. Guardians: `people` → `student_guardian_relationships` → `users` (`personId`) | PRD §1, §2, §4 |
| Nothing "current" on the Student | No Class/Section/Roll field on `student_profiles`. Current placement is read from the open enrollment and section assignment through `studentService.getContext()`. The directory uses an aggregation `$lookup` on open rows (indexes below), not a denormalised copy | PRD §2 / §62 guardrails |
| Effective dating | Rows store `effectiveFrom`, `effectiveTo?`, `cancelledAt?` and an explicit `isOpen` flag kept by the services (`false` once ended, cancelled or closed). **Display status is computed** from dates in the school timezone (`PLANNED`, `ACTIVE`, `ENDED`, `CANCELLED`). Enrollments add `closeOutcome` (`COMPLETED`, `PROMOTED`, `REPEATED`, `WITHDRAWN`, `TRANSFERRED`), which is the PRD's enrollment status after it closes | Same approach as Modules 2–3 (no nightly status job). `isOpen` makes the "one open row" partial unique indexes possible |
| Rows are never deleted | Enrollments, assignments, subjects, relationships and TCs end, close or cancel. Hard delete only for a `DRAFT` student with no history, documents or guardians that others use | PRD §27 "no generic Delete Student" |
| Student lifecycle ≠ enrollment status | `DRAFT → ADMISSION_PENDING → ACTIVE ↔ TEMPORARILY_INACTIVE / SUSPENDED`, `ACTIVE → WITHDRAWAL_INITIATED → WITHDRAWN / TRANSFERRED_OUT`, and `COMPLETED_SCHOOLING`. Moves are endpoints on a state machine (`students/lifecycle.ts`, same shape as Modules 1 and 3); PATCH rejects `status` | PRD §21 |
| Admission Number | Unique per school (`admissionNumber` stored uppercase, trimmed). Pattern tokens: `{PREFIX}`, `{LOC}`, `{YEAR}` / `{SESSION}`, `{SEQ:n}` (zero-padded). Counters live in `number_sequences` and advance with an atomic `$inc`, scoped by the rendered non-sequence part of the pattern. AUTO and MANUAL modes. Migration always uses a typed number and keeps it exactly as given. Gaps are allowed (a rolled-back create may burn a number) | PRD §5.1 |
| Roll Number | Belongs to the section assignment, unique among open assignments of a section. Modes: `MANUAL`, `AUTO_SEQUENTIAL` (next free number in the section) and bulk assignment | PRD §15.3 |
| Parent access chain | `authorizeParentAccess(user, studentId, capability)` in one module (`students/parent-access.ts`) used by every portal route. It checks user ACTIVE and role `PARENT` → `users.personId` → an open relationship with `hasPortalAccess` and the capability flag (`academicAccess` / `financialAccess`) → student in the same tenant. Anything else returns **404** (no enumeration) and writes a `STUDENT_ACCESS_DENIED` security event. Revoking or ending a relationship takes effect on the next request, because nothing is cached | PRD §13, SEC-SPM-01 |
| Faculty access | Derived, never granted by role alone: a Faculty user sees a Student only if the Student's open section assignment is in a section the faculty has an active `faculty_academic_assignments` row for (class-level for `COORDINATOR` / `HOD`). Result: `FacultyStudentSummaryDTO`. Anything else is 404 + `STUDENT_ACCESS_DENIED` | PRD §36 |
| Staff access | `STAFF` has no student permissions in v1 ("Staff role alone grants no universal Student data"). Capability grants per user are deferred | PRD §36 |
| DTOs, not documents | Six mappers: `toStudentDirectoryDTO`, `toStudentAcademicContextDTO`, `toStudentAdminProfileDTO`, `toFacultyStudentSummaryDTO`, `toParentStudentSummaryDTO`, `toExportRow(purpose)`. No route serialises a Mongoose doc | PRD §37, same pattern as Module 3 |
| Field classification in code | `shared/data-classification.ts` gains every student, guardian, enrollment and identifier field. The unit test from Module 3 fails when a path has no class or a DTO leaks a class it isn't allowed. Child fields default to `PERSONAL`; identifiers and documents are `RESTRICTED` | PRD §38 |
| External identifiers | `student_external_identifiers`, never columns on the profile. Values other than `LEGACY_ERP_ID` / `SCHOOL_CUSTOM` are encrypted with Module 3's `encryptField`, shown masked (`last4`), and looked up for duplicate detection through a keyed **blind index** (`valueHash` = HMAC-SHA256 of the normalised value, key `IDENTIFIER_HASH_KEY`). Aadhaar is not an allowed type for students | PRD §8, §22. Module 3 didn't need a blind index; here PRD §8 does |
| Private files | Student documents reuse `PrivateStorage` + signed `GET /files/:signedToken` (60 s, `attachment`, `no-store`, `nosniff`) | PRD §18.1 |
| IDs | UUID v4 `_id`, camelCase API (`studentId`, `personId`, `studentEnrollmentId`). Other modules store `studentId` and `studentEnrollmentId`, never the admission or roll number | Same as Modules 1–3 |
| Concurrency | `PATCH /students/:id` and section changes take `expectedVersion` (the document `version` counter) and return `VERSION_CONFLICT` on mismatch. High-impact operations are separate explicit endpoints, never autosaved | PRD §50 |
| Persistent context | Session + Location live in the UI header context bar and are sent as query params. The server defaults the session to the ACTIVE one and validates both through `academicService` / `masterService`. Actions never ask for School, Location or Session again | PRD §3.1 |

### Simplifications versus the PRD (deliberate)

| PRD item | What we do | Deferred |
|---|---|---|
| Multiple contacts / addresses per person | Embedded on `people` as in Module 3 (one address, one emergency contact per person). Guardian phone/email are the match keys (normalised: digits only with country code, lowercase email) | `person_contacts`, `person_addresses` |
| Parent matching scope | Searches Guardian persons (people with at least one relationship) in the tenant. Employee-only persons are not matched, so HR data never leaks into admissions | Matching a teacher who is also a parent |
| Dual-role accounts | A guardian whose email already belongs to a non-`PARENT` user can't be given portal access (`ACCOUNT_ROLE_CONFLICT`). The relationship is still saved | One user with Faculty + Parent roles |
| Contact verification | Parent account activation through the emailed single-use link proves the email. Phone is stored unverified | SMS OTP, phone login |
| Subject rules | Module 2 choice groups (`REQUIRED_ALL`, `CHOOSE_ONE`, `CHOOSE_N`, `OPTIONAL`) and constraints (`REQUIRES`, `EXCLUDES`) | Board restrictions (not modelled in Module 2) |
| Parent selects Subjects | Admin selects. `selectionSource` already has room for a Parent value | Parent selection flow |
| Exit clearances | `duesClearanceStatus` on the TC (`PENDING`, `CLEARED`, `WAIVED`) set by an admin. A `clearanceChecks` registry (empty) is the hook where Fees, Library and Transport register later | Real clearance feeds |
| TC document | TC record + printable HTML view + optional upload of the signed scan as a student document | Generated PDF with school letterhead |
| Consent evidence, age-aware flags | A `consentRecordedAt?` and `privacyNoticeVersion?` field on the profile, not enforced | Consent workflows |
| `ARCHIVED` student state | Not used. Terminal states are `WITHDRAWN`, `TRANSFERRED_OUT`, `COMPLETED_SCHOOLING` | Retention and archival rules |
| Pickup authorisation, communication priority | Stored and editable on the relationship, no consumer yet | Communication / Transport modules |
| Bulk import | Synchronous CSV, up to 2,000 rows, staged in `student_imports` | Async jobs, XLSX |
| Exports | Synchronous CSV, stored privately, expires in 15 min (Module 3 mechanism) | Job queue |
| Staff "capability" access | Static role permissions | Per-user capability grants |
| Parent self-service UI | Parent portal in v1 shows the child switcher, child summary, guardians/contact edit and change requests. Timetable, attendance, fees and results screens arrive with their modules | Downstream parent pages |

## Part 1: Student identity, family and Parent access (backend)
**Stories:** SPM-01, SPM-02, SPM-03, SPM-04, SPM-05, SPM-06, SPM-07, SPM-08, SPM-09, SPM-12, SPM-13, SPM-22, SPM-23, SPM-24, SPM-25, SPM-33, SEC-SPM-01 (parent half), SEC-SPM-02, SEC-SPM-03

**Shared contract and permissions**
1. Enums, Zod schemas (`.strict()`, so `status`, `lifecycleStatus`, `isOpen`, `role` and unknown keys in a PATCH are rejected), DTOs and error codes in `backend/src/shared`. Move the `people` model to `platform/identity/people/` (re-export from `staff`).
2. New permissions. School Admin has all; Faculty gets `student:directory` (still limited to their own students, see Part 2); Staff and Parents get none. Parent portal routes need only a signed-in `PARENT` user plus the access chain.
   - `student:directory`: directory fields
   - `student:view`: admin profile, guardians, history
   - `student:view_personal`: DOB, gender, address, guardian contact on the profile
   - `student:manage`: create, edit, lifecycle moves (Part 1), settings
   - `student:guardians`: add/link/end guardians, set Primary
   - `student:portal`: enable/revoke portal access, invite parents
   - `student:documents`: upload, download, delete
   - `student:approve_changes`: decide change requests
   - Added in Parts 2–3: `student:enroll`, `student:lifecycle`, `student:tc`, `student:import`, `student:export`
3. Error codes (examples): `ADMISSION_NUMBER_TAKEN`, `ADMISSION_NUMBER_REQUIRED` (manual mode), `ADMISSION_NUMBER_AUTO` (typed number in auto mode), `POSSIBLE_DUPLICATE_STUDENT`, `PRIMARY_GUARDIAN_EXISTS`, `GUARDIAN_RELATIONSHIP_EXISTS`, `GUARDIAN_EMAIL_REQUIRED`, `ACCOUNT_ROLE_CONFLICT`, `PORTAL_NOT_ENABLED`, `STUDENT_READ_ONLY`, `STUDENT_HAS_HISTORY`, `VERSION_CONFLICT`, `IDENTIFIER_TYPE_NOT_ALLOWED`, `DOCUMENT_TYPE_INVALID`.
4. Extend `shared/data-classification.ts` and its unit test for every new path.

**Settings and Admission Numbers (SPM-03)**
5. `GET/PUT /student-settings` (`student:manage`). The pattern is validated by rendering a sample (`GPS/2027/00482`). `POST /admission-numbers/generate { admissionSessionId?, locationId? }` returns a preview **without consuming** the sequence. The real number is allocated inside the create transaction.
6. Uniqueness is on the normalised uppercase number. Duplicate → `ADMISSION_NUMBER_TAKEN`. In AUTO mode a typed number is refused, except in migration mode (Part 3 import and `mode: EXISTING_MIGRATION`), which keeps the historical number exactly.

**Student and admission identity (SPM-01, SPM-02, SPM-33)**
7. `POST /students` creates the person, the profile and the admission (`NEW_ADMISSION` or `EXISTING_MIGRATION`) in **one transaction**. Required: name, admission date (required, or taken from the migration row, and never the ERP onboarding date for migrated students), admission class offering, session and location (defaults from the context). Optional details never block creation unless the school marks a document or field mandatory. `lifecycleStatus` starts as `DRAFT` and becomes `ADMISSION_PENDING` or `ACTIVE` through Part 2's placement step. Part 2 extends this same endpoint with `placement` and `guardian` blocks for Quick Add, so no separate create route exists.
8. `POST /students/duplicate-check { name, dateOfBirth?, admissionNumber?, guardianPhone?, identifiers? }` returns ranked candidates with the reason (admission number, legacy ID, identifier blind-index hit, exact/near name + DOB, guardian contact + matching child attributes). `POST /students` runs it first and returns `POSSIBLE_DUPLICATE_STUDENT` with the candidates unless `confirmNotDuplicate: true` is sent. **Never auto-merge.**
9. `GET /students/:id` returns `StudentAdminProfileDTO` (+ personal fields with `student:view_personal`). `PATCH /students/:id` is an allowlist (names, preferred name, DOB, gender, address, previous school, category, source, remarks) guarded by `expectedVersion`. Legal name and DOB go direct for admins; Parents use change requests below.
10. Lifecycle endpoints on the state machine: `POST /students/:id/status { to: ACTIVE | TEMPORARILY_INACTIVE | SUSPENDED, reason? }`. Withdrawal and readmission moves belong to Part 3. Illegal moves return `INVALID_STATUS_TRANSITION`. Non-`ACTIVE` students can't get new enrollments (checked in Part 2). Terminal students are read-only (`STUDENT_READ_ONLY`) but remain searchable.
11. `DELETE /students/:id`: only while `DRAFT` with no enrollment, document, relationship or login (`STUDENT_HAS_HISTORY` otherwise).
12. `GET/POST /students/:id/external-identifiers`, `POST …/:identifierId/end`. Values are encrypted or stored plain per type, with the blind index written alongside. Responses always carry `last4` only. A reveal isn't offered in v1.

**Guardians, matching and siblings (SPM-04..09)**
13. `POST /guardians/match { phone?, email?, name? }` normalises the contact and returns existing Guardian persons with name, masked contact, verified-account flag and currently linked children. Ambiguous matches (same phone, different name) are returned as `AMBIGUOUS` for side-by-side comparison. The server never merges.
14. `POST /students/:id/guardians` creates a new guardian person and the relationship in one transaction, **only** if the caller passes `matchReviewed: true` (the matches shown were reviewed). `POST /students/:id/link-existing-guardian { guardianPersonId, relationshipType, … }` links the same person without re-entering contact data (siblings reuse the Parent). `GET /students/:id/guardians` lists relationships with portal and account state.
15. Primary Guardian: normally one open per student. `PATCH /student-guardian-relationships/:id { isPrimaryGuardian: true }` swaps the primary in one transaction (the old primary stays a guardian). Emergency-contact, portal, communication priority and pickup flags are independent: **an emergency-only grandmother with no portal access is a valid relationship**. The first guardian of a student becomes Primary automatically.
16. `POST /student-guardian-relationships/:id/end { effectiveTo, reason }` ends the relationship (history kept) and, in the same transaction, revokes the portal access for that child only. `GET /guardians/:personId/students` powers *Add / Link Child* from the Parent profile.
17. `PATCH /guardians/:personId` edits the guardian's own contact once, and every child sees it (Zero Re-entry). Changing the email of a person with a PARENT account is blocked here (`ACCOUNT_EMAIL_LOCKED`); it goes through the account flow.

**Parent portal access and accounts (SPM-22..24, SEC-SPM-01)**
18. `POST /student-guardian-relationships/:id/enable-portal { academicAccess?, financialAccess? }` needs `student:portal`. It requires a guardian email (`GUARDIAN_EMAIL_REQUIRED`), checks for an existing user by email or `personId` and **reuses it** if it is a `PARENT`, or creates a `PENDING_ACTIVATION` PARENT user with a single-use 72 h activation link (Module 3's tokens, notifier and `/auth/activate`). A user with another role → `ACCOUNT_ROLE_CONFLICT`. Enabling a second child for an active Parent sends no new invitation.
19. `POST /student-guardian-relationships/:id/revoke-portal` removes access for that child only, leaves the account active for other children, audits it and writes a `PARENT_ACCESS_REVOKED` security event. Suspending the user (Module 3 admin routes) is the separate account-level control.
20. `POST /parents/invitations/bulk { relationshipIds[] | filter }` creates one invitation per distinct guardian person (not per child), skips active accounts and returns `{ invited, alreadyActive, skipped: [{reason}] }`. Confirmation is the UI's job, the server is idempotent (a pending token is reissued, not duplicated). Rate limited.
21. `GET /parents/me/students` returns the authorised children for the child switcher: name, class and section when known, capability flags. It uses only the open relationships of the signed-in user. `GET /parents/me/students/:studentId` returns `ParentStudentSummaryDTO` (Part 2 adds the academic block). Every portal route calls `authorizeParentAccess`; the same user asking for a student they are not linked to, or an ended relationship, gets 404 + a security event.
22. `PATCH /parents/me/profile`: allowlist (preferred name, secondary phone, address). Direct and audited.

**Documents and previous school (SPM-12, SPM-13, SEC-SPM-03)**
23. `POST /students/:id/documents` (multipart, 5 MB): authorization, magic-byte sniffing (PDF/PNG/JPG), `scanFile()`, random private key, sha256. `POST /student-documents/:id/download` re-checks access and returns a signed 60 s URL. Every download, denial and delete is audited. Parents get no document access in v1.
24. `GET /students/:id/documents/summary` returns completeness from `requiredDocumentTypes`: `{ complete: 5, required: 6, missing: ['PREVIOUS_SCHOOL_RECORD'] }` for the inline "Documents 5/6" action. Previous-school fields live on the admission and are optional unless the school makes them mandatory.

**Change requests (SPM-25)**
25. Admin or Parent: `POST /students/:id/profile-change-requests { fieldCategory, value, reason? }` (Parents through `/parents/me/students/:studentId/change-requests`, same access chain). Old and proposed values are stored encrypted, one pending per category. Admin: `GET /student-profile-change-requests?status=`, `POST …/:id/approve` (applies the change in the same transaction) and `/reject { note }`, requiring `student:approve_changes`.

**Isolation, audit and in-process API**
26. Every mutation writes an audit event in the same transaction with field diffs (identifier values and DOB changes show `[redacted]`). `GET /students/:id/history` merges audit rows and relationship history. Cross-tenant IDs return 404 on every route. Parents get 403 on admin routes.
27. `studentService` (in-process, extended in Parts 2–3): `getStudentSummary()`, `assertStudentUsable(purpose)`, `listGuardians(studentId)`, `getGuardianRelationship(id)` (used by Communication later).

## Part 2: Academic placement, Quick Add and Student context (backend)
**Stories:** SPM-10 (server side), SPM-14, SPM-15, SPM-16, SPM-17, SPM-18, SPM-19, SPM-20 (API), SPM-21, SPM-26, SPM-37, SEC-SPM-01 (faculty half), SPM-UX-03, SPM-UX-04, SPM-UX-08, SPM-UX-09, SPM-UX-10

**Enrollment (SPM-14)**
1. `POST /students/:id/enrollments { academicSessionId?, locationId?, classId, academicProgrammeId?, enrollmentType, enrollmentDate }`. The caller sends a human-readable **Class**, and the server resolves the Class Offering for the session and location. A missing offering is `CLASS_NOT_OFFERED`. Every reference is checked through `academicService` with `purpose: NEW_ASSIGNMENT` (PUBLISHED/ACTIVE session, ACTIVE offering, location ACTIVE through `masterService`). The student must be `DRAFT`, `ADMISSION_PENDING` or `ACTIVE` (`STUDENT_READ_ONLY` otherwise).
2. A second open enrollment in the same session is blocked (`ACTIVE_ENROLLMENT_EXISTS`, backed by the partial unique index). `PATCH /student-enrollments/:id` changes only the programme (→ revalidation, see item 12) and `enrollmentDate`. `POST /student-enrollments/:id/complete { outcome }` closes it with a `closeOutcome`. `GET /students/:id/enrollments` returns the full history. Completing, promoting and withdrawing are the only ways an enrollment ends; none deletes it.
3. Creating the first enrollment moves a `DRAFT` / `ADMISSION_PENDING` student to `ACTIVE` when the enrollment is current, in the same transaction.

**Section assignment and Roll Number (SPM-15, SPM-16, SPM-26)**
4. `POST /sections/recommend { classOfferingId, locationId, academicSessionId }` ranks ACTIVE sections of that class offering by free capacity (strength is counted from open assignments) and school preference. It returns `[{ sectionId, name, strength, capacity, rank, reason }]`, for example *VIII-A 39/40, VIII-B 34/40*. The first ranked section is only a suggestion; the human decides.
5. `POST /student-enrollments/:id/section-assignment { sectionId, rollNumber?, effectiveFrom? }` checks that the section belongs to the enrollment's class offering (`SECTION_CLASS_MISMATCH`), is ACTIVE, and has capacity. Over-capacity follows `overCapacityPolicy`: `WARN` returns a `warnings[]` entry and proceeds, `BLOCK` returns `SECTION_FULL`. The roll number is assigned per `rollNumberMode` (auto = next free number in the section) and checked for uniqueness among open assignments (`ROLL_NUMBER_TAKEN`).
6. `POST /student-section-assignments/:id/change { sectionId, effectiveFrom, reason, expectedVersion }` is the mid-session Section change: same class context, ACTIVE section, capacity check. It ends the old assignment the day before, creates a new one and records a `SECTION_CHANGE` transfer event (Part 3's model, created here), all in one transaction. The old row keeps its history (Apr–Sep VIII-A, Oct–Mar VIII-B).
7. `POST /sections/roll-numbers/bulk { sectionId, strategy: 'ALPHABETICAL' | 'ADMISSION_NUMBER' | 'KEEP_EXISTING_FILL_GAPS', dryRun? }` assigns or reassigns roll numbers for a whole section atomically. `dryRun` returns the proposed list. Changes are audited as one event with a count.

**Subjects (SPM-17, SPM-18, SPM-19, SPM-UX-09/10)**
8. `POST /student-enrollments/:id/subjects/initialize` is called automatically by the enrollment create and promotion. It adds every ACTIVE `MANDATORY` subject offering of the class offering (and `REQUIRED_ALL` groups) as `AUTO_MANDATORY`, and returns `{ added: 5, pendingChoices: [{ groupId, name, min, max }] }`, which is the "5 mandatory Subjects added automatically" message. It is idempotent.
9. `POST /student-enrollments/:id/subjects/validate-selection { subjectOfferingIds[] }` evaluates a candidate selection with a pure function in `students/subjects.ts`, reading Module 2's `listChoiceGroupsFor` and `listConstraintsFor`: `CHOOSE_ONE` / `CHOOSE_N` min and max, `REQUIRES`, `EXCLUDES`, and that every id belongs to the class offering and is ACTIVE. The answer lists `violations[]` with a clear message and `alternatives[]` (the valid options for the group). It writes nothing.
10. `POST /student-enrollments/:id/subjects { subjectOfferingIds[], selectionSource }` runs the same validation and saves the selection (`SUBJECT_SELECTION_INVALID` with the same payload on failure). `POST /student-subject-enrollments/:id/end { effectiveTo, reason }` ends one subject (mandatory ones can't be ended, `MANDATORY_SUBJECT`). `GET /student-enrollments/:id/subjects` returns current and historical rows. Students with unresolved choices are findable for Needs Attention (Part 3).
11. Programme: `academic_programme_id` stays nullable. Programmes come from Module 2 and only help derive subjects (`PROGRAMME_DERIVED`). Nothing hard-codes Science / Commerce / Humanities.
12. **Programme change:** `PATCH /student-enrollments/:id { academicProgrammeId, preview: true }` returns `{ retained, added, invalid, unresolved }` without committing. The same call without `preview` applies it and ends only the invalid subject rows. Historical subject enrollments are preserved.

**Quick Add and onboarding (SPM-10, SPM-UX-03/04)**
13. `POST /students` accepts the optional blocks `{ placement: { classId, sectionId?, programmeId? }, guardian: { existingPersonId | contact, relationshipType, enablePortal? } }`. With them, **one transaction** creates the person, profile, admission (auto number), enrollment, section assignment with roll number, mandatory subjects and the guardian relationship (reusing the matched Parent). The response lists `derived: { admissionNumber, section, rollNumber, mandatorySubjectsAdded, parentReused }` so the UI can show what the system decided. School, Location and Session come from the context. Without `placement` it saves a `DRAFT` (progressive completion); the same endpoint serves the comprehensive wizard step by step.
14. `GET /students/:id/completeness` returns the missing requirements (guardian, section, documents, subject choices) used for Needs Attention and the profile checklist.

**Directory, context and Faculty access (SPM-20, SPM-21, SPM-37, SEC-SPM-01)**
15. `GET /students?sessionId=&locationId=&classId=&sectionId=&status=&search=&portal=&missing=…`: paginated; search by name, admission number, roll number, guardian name/phone and external identifier (blind index, exact only). Filters from PRD §33 that need Part 3 data (withdrawal pending, TC pending) are added there. Returns `StudentDirectoryDTO` rows with current class, section and roll for the chosen session.
16. `GET /students/:id/academic-context` returns `StudentAcademicContextDTO`: open enrollment, location, class, section, roll, programme, subject enrollments, history summary.
17. `GET /student-context?student_id=&academic_session_id=&date=` is the canonical downstream contract: the enrollment valid on that date, with effective-dated section and subjects for that date. Timetable, Attendance, Fees and Exams consume this and `studentService.getContext()`; none reconstruct state or keep their own roster.
18. Faculty routes: `GET /faculty/students` and `GET /sections/:id/students` return `FacultyStudentSummaryDTO` (name, admission number, roll, section, guardian primary contact name only) limited by the Faculty access rule in the decisions table. Everything else is 404 + `STUDENT_ACCESS_DENIED`. `ParentStudentSummaryDTO` gains the academic block (class, section, roll, subjects) for portal-enabled `academicAccess` only.
19. Register on the **academic dependency registry** (class offering, section, subject offering, programme with open enrollments or assignments block the unsafe change on an ACTIVE session) and the **location registry** (open enrollments block archive, any enrollment locks the code). `studentService` gains `getContext()`, `listStudentsForSection(sectionId, date)`, `countStrength(sectionId)`.

## Part 3: Transfers, promotion, exit, import and Needs Attention (backend)
**Stories:** SPM-11, SPM-27, SPM-28, SPM-29, SPM-30, SPM-31, SPM-32, SPM-34, SPM-35, SPM-36, SEC-SPM-02 (exports), SEC-SPM-04, SPM-UX-11, SPM-UX-12, SPM-UX-13, SPM-UX-14, SPM-UX-15, SPM-UX-20

**Location transfer (SPM-27)**
1. `POST /students/:id/location-transfer/validate { toLocationId, effectiveDate, classId?, sectionId? }` is a dry run. It resolves the destination Class Offering, finds a section (recommendation reused from Part 2), and compares subjects: matches by Module 2 `subjectId` are `retained`, new mandatory ones are `added`, unmatched current ones are `ended`, and unmapped required choices are `unresolved`. Nothing is copied silently.
2. `POST /students/:id/location-transfer { …validated payload, mappingConfirmed: true, reason }` needs `student:lifecycle`. If `unresolved` is not empty and `mappingConfirmed` is false it returns `ACADEMIC_MAPPING_REQUIRED`. In one transaction it closes the old enrollment (`TRANSFERRED`), creates the destination enrollment (`MID_SESSION_TRANSFER`, linked by `previousEnrollmentId`), the section assignment and the re-evaluated subject rows, and writes a `LOCATION_TRANSFER` event. `student_id` and the admission identity stay the same. A future-dated transfer stays `PLANNED` until its date through the computed status.
3. `GET /students/:id/transfers` returns the movement history (section changes and location transfers).

**Promotion and rollover (SPM-28, SPM-29, SPM-UX-12/13)**
4. `GET /promotions/readiness?fromSessionId=&toSessionId=&locationId?&classId?` evaluates every open enrollment in the source session and returns `{ evaluated: 1200, ready: 1167, needsReview: 33, groups: [{ reason, count }], exceptions: [{ studentId, reasons[] }] }`. The exceptions follow PRD §25.3: missing next Class (the offering with the next class sequence in the target session), student marked Leaving, pending academic decision (`HOLD`), programme incompatibility, unresolved subject choice at the destination, missing destination location or section, enrollment already closed or not open, and a manual override flag.
5. `POST /promotions/recommend` returns the proposed next class, location and section per student (the recommendation is only a proposal). `PUT /students/:id/promotion-decision { fromEnrollmentId, decision: PROMOTE | REPEAT | LEAVING | HOLD, targetClassId?, reason? }` stores one human decision. `POST /students/:id/repeat` is the shortcut for `REPEAT`.
6. `POST /promotions/bulk { fromSessionId, toSessionId, scope, idempotencyKey, confirm: true }` (`student:lifecycle`) promotes the **ready cohort and decided exceptions only**, never `HOLD` or `LEAVING`. For each student, in per-student sub-transactions inside one run: closes the old enrollment (`PROMOTED` or `REPEATED`, **never edited otherwise**), creates the next-session enrollment (`PROMOTED` / `REPEATING`, `promotedFromEnrollmentId` set), a section assignment and roll number per the recommendation, and re-initialises subjects. Admission number, guardians, parent account, identifiers and documents are carried by reference, untouched. A failing student is reported in `failed[]` and doesn't stop the others. The target enrollment may be `PLANNED` if the target session isn't active yet. Re-sending the same `idempotencyKey` returns the original result. `confirm` is mandatory, since the UI asks for it.
7. Leaving students are excluded and appear in the exit queue (item 9). A repeat creates a new enrollment in the same class offering of the next session with the previous enrollment kept as `REPEATED`.

**Withdrawal, Transfer Certificate and readmission (SPM-30..32)**
8. `POST /students/:id/withdrawal { leavingDate, reasonCategory, reasonNote?, destinationSchool?, tcRequired }` sets the student to `WITHDRAWAL_INITIATED`, creates a `student_withdrawals` row and a TC request when `tcRequired`, and runs `clearanceChecks` (empty registry today, plus the TC's `duesClearanceStatus`). `POST /students/:id/withdrawal/complete` (needs the TC `APPROVED` or `ISSUED` when required) closes the open enrollment (`WITHDRAWN`) and ends open section assignments, subjects and portal access per school choice (default: portal stays read-only until the leaving date, then revoked by `processDueWithdrawals()`), and moves the student to `WITHDRAWN` or `TRANSFERRED_OUT`. `…/cancel` returns to `ACTIVE`. All history is kept. There is **no delete**.
9. `processDueWithdrawals()` in `students/jobs.ts` completes withdrawals whose date has arrived, using the same pattern as `processDueExits` (started in `server.ts`, never `app.ts`, called directly in tests).
10. TC workflow: `POST /students/:id/transfer-certificates`, `PATCH /transfer-certificates/:id` (only before `APPROVED`), `POST …/approve`, `POST …/issue`, `POST …/duplicate`. States run `REQUESTED → UNDER_REVIEW → PENDING_CLEARANCE → APPROVED → ISSUED`. The certificate number is generated at **issue** from `tcNumberPattern` through the sequence mechanism. An issued TC isn't editable (`TC_ISSUED_LOCKED`); a correction needs a separate permission (`student:tc` + `reason`) and is audited with a before/after diff. A duplicate is a new `DUPLICATE` row with the suffix number, an explicit status `DUPLICATE_ISSUED` and its own audit event. `GET /transfer-certificates/:id/print` returns the printable data. A signed copy can be uploaded as a `TRANSFER_CERTIFICATE` student document.
11. `POST /students/:id/readmit { admissionNumberPolicy?, classId, locationId?, sectionId?, … }`: finds the existing student (never creates a second person), follows `readmissionNumberPolicy` (`RETAIN` keeps the number; `ISSUE_NEW` creates a new `READMISSION` admission and marks the old one not current; **never silently issues a new number** and always shows which policy applied), creates a new current enrollment (`READMISSION`), section and subjects, and **revalidates guardians and portal access**: ended relationships stay ended, open ones are listed for confirmation. The student returns to `ACTIVE`.

**Existing-student migration and bulk import (SPM-11, SPM-34, SPM-UX-14/15)**
12. `POST /students/imports` (multipart CSV, ≤ 2,000 rows, mode `EXISTING_STUDENT` or `NEW_ADMISSION`), `POST …/:id/map`, `POST …/:id/validate`, `GET …/:id/issues`, `POST …/:id/commit`. Upload reads headers and **auto-maps** common names (Student Name, Admission No, Class, Section, Roll No, Father Mobile, Mother Mobile, Admission Date…), returning the mapping for confirmation. The same file hash in the same mode returns the existing import (idempotent).
13. Validation touches nothing. Per row it checks: duplicate admission number (in the file and in the school), unknown location / class / section, section-class mismatch, class not offered at the location, invalid session, possible duplicate student, guardian issues (missing contact, parent match found, ambiguous match), section capacity warning, invalid subject choice (the Part 2 evaluator), and roll number conflict. The result is **issue-centric**: `{ rows: 1000, ready: 965, needsAttention: 35, byCategory: [{category, count}] }`, and `GET …/issues?category=` returns the issue rows with `suggestion` text. An error report downloads as CSV (row, field, error, suggested fix) with the CSV-injection escaping from Module 3.
14. `POST /students/imports/:id/resolve { rowNumber, resolution: 'LINK_EXISTING_GUARDIAN' | 'USE_EXISTING_STUDENT' | 'SKIP' | 'EDIT', values? }` resolves exceptions without re-uploading. `commit` processes only `READY` and resolved rows, one transaction **per row** (so no half-created student), reuses matched guardians, preserves the historical Admission Number and original admission date, creates the enrollment, section, roll, subjects (mandatory + migrated choices), identifiers and optional portal invitation state, then marks the row `COMMITTED`. A retry skips committed rows, so no duplicate students. One audit event per import with counts, never per-row PII.

**Needs Attention, dashboard and filters (SPM-36, SPM-UX-11, SPM-UX-20)**
15. `GET /students/needs-attention?category=&sessionId=&locationId=` computes (no stored copy) the categories from PRD §3.2: Student Setup (missing section, incomplete admission), Family (no Primary Guardian, potential duplicate parent), Parent Access (invitation pending, access missing), Subjects (elective incomplete or invalid), Documents (required missing), Promotion (undecided), Transfers (mapping required), Exit (TC or clearance pending) and Data Quality (possible duplicate student, conflicting identifiers). It returns counts per category and paged rows with an explicit `missing[]` and the action to take. The directory gains the remaining PRD §33 filters: `withdrawalPending`, `tcPending`, `subjectChoicePending`, `missingGuardian`, `missingSection`, `missingDocuments`, `portal`.
16. `GET /students/dashboard?sessionId=&locationId=` returns the KPIs (active students, new admissions, students by class and location, Parent Portal activation %, withdrawals this session) and the **action queue counts**, which are the same numbers as Needs Attention.

**Export, audit and security (SEC-SPM-02, SEC-SPM-04, SPM-35)**
17. `POST /students/exports { purpose: STUDENT_DIRECTORY | STUDENT_ACADEMIC | GUARDIAN_CONTACTS, filters }` (`student:export`, separate from view). Allowlists per purpose; DOB, identifiers, documents and health data are never exportable in v1. CSV escaping, private storage, signed URL, 15 min expiry. Audit records actor, purpose, filters and row count, and a `STUDENT_EXPORT` security event.

## Assumptions to confirm
1. One school per tenant (as before), so routes don't carry a `schoolId`; `schoolId` is still stored on every student record.
2. `STAFF` gets no student permissions and Faculty see only the students in their own sections (and classes, for coordinators and HODs). If a school-wide Student directory for staff is wanted, it needs a per-user capability grant (deferred).
3. A guardian's email is required before the portal can be enabled; phone-only guardians stay valid for emergency and communication but can't log in (no SMS or phone login yet).
4. Matching never merges, and employee-only people aren't matched as parents (dual-role teacher-parents are deferred).
5. Date of birth is restricted in exposure (never in lists, directories, exports or the Faculty/Parent summaries beyond the child's own parent) but not field-encrypted, so ages can be computed later. External identifiers are encrypted with a blind index for duplicate detection.
6. Admission numbers may have gaps (a rolled-back create can burn a number). If a gapless sequence is a legal requirement, it needs a different allocation approach.
7. Withdrawal completion revokes portal access on the leaving date; a school that wants longer read-only access needs a setting later.
8. Parent portal pages for timetable, attendance, fees and results arrive with their modules; this module only owns the access association and the child summary.
9. Bulk import is synchronous up to 2,000 rows; larger schools split the file. Async jobs, XLSX, and real clearance feeds from Fees, Library and Transport are deferred.
10. Fee billing, structured health records, biometrics and Student logins stay out of scope (PRD §2: Student is not a login user in V1). Medical papers can only be stored as private documents.
