# SchoolVerse — Module 7: Fees, Billing, Collections, Payroll, Tax & Accounting

Source of truth: `../School_ERP_Module_07_Fees_Billing_Payroll_Financial_Management_PRD_v2.0_Offline_First.pdf` (+ the Epic brief **FIN-ERP**)
Depends on: Module 1 (school, locations, state for GST), Module 2 (sessions, classes), Module 3 (employees, departments, bank details, exits), Module 4 (students, guardians, parent portal, promotion, TC). **Module 6 is skipped for now.** Nothing here needs it. Module 5 (rooms) is not used.
Visual reference: same SchoolVerse theme and accents as Modules 1–5.

**Goal, in plain words:** one place where the school knows every rupee: what each family owes, what was paid, what each teacher earns, what the school spends, what the bank shows, and what tax is due. The system does the normal work by itself (assign fees, make bills, match bank lines, work out salaries). People only look at the **exceptions**. There is **no payment gateway**. Money moves through the school's own bank, UPI and cash. SchoolVerse records it, checks it, matches it and explains it.

**Core principle:** Configure once. Automate the standard. Surface the exceptions. Explain every rupee.

**The chain this module must run (the Epic is done only when all of it works end to end):**

Configure Finance → Create Fee Structure → Auto-assign Students → Generate Bills → Apply Concessions and Tax → Collect and Verify Payments → Allocate → Issue Receipts → Reconcile Bank → Manage Outstanding → Run Payroll → Record Salary Payment → Manage Expenses → Post Accounting Entries → Close the Period → Produce Reports. Every step is auditable, explainable and permission-controlled.

**Golden rules (what we must never break):**
- **Money is whole paise** (a whole number, ₹1 = 100 paise). Never decimals or floats. Screens show rupees.
- **One book.** Everything that moves money writes one **balanced journal** (debits = credits). A posted journal never changes. A mistake is fixed with a new reversing journal.
- **"Said" is not "seen".** A parent's UPI claim, a printed bank file and a cheque in hand are **not** received money. Only **verified** money counts, and the receipt comes after.
- **A balance is worked out, never typed.** It comes from bills, payments, credits and adjustments. There is no "edit outstanding amount" box anywhere.
- **A family is a view, not a ledger.** Each child keeps their own account. Family totals are only added up on screen.
- **Issued papers never change.** Bills, receipts and payslips keep their number and content. A correction is a new linked paper (credit note, cancelled receipt, correction run).
- **Salary is private.** An employee sees only their own payslip. Payroll data needs a special permission.
- **Nothing used is deleted.** We archive, reverse or end-date.
- **Tax is a setting, not a guess.** Which fee is exempt or taxable is chosen by the school (with their accountant). We do not hard-code it.
- Security is checked on the server. Hiding a button is never the protection.

## Words used in this module (plain meaning)

| Word | Plain meaning |
|---|---|
| Fee Head | A kind of charge: Tuition, Transport, Exam fee |
| Fee Plan | The price list for a class, with when each fee is due. It has versions |
| Bill (Fee Document) | What a family owes for one period. Once issued, it never changes |
| Concession | A discount or scholarship (sibling, staff child, merit). It is **not** a payment |
| Claim | A parent says "I paid ₹4,000 by UPI". Not money yet |
| Collection | Money the school actually received (cash, cheque, UPI, bank transfer) |
| Verify | Staff confirm the money really arrived (cash counted, or seen in the bank) |
| Allocate | Decide which bill(s) a payment pays. One payment can pay many bills |
| Advance (Credit) | Money paid with no bill to pay yet. It is a **debt the school owes**, not income |
| Receipt | The final paper that proves a verified payment, with a number that never repeats |
| Journal | One accounting entry: "money came from here, went there", always balanced |
| Ledger | The list of all entries for a student or an account |
| Reconcile | Match the school's records to the bank statement line by line |
| Period close | Lock a month so old numbers cannot be changed quietly |
| GST / ITC | Tax charged on sales / tax paid on purchases that may be claimed back |
| Payslip | The salary statement of one employee for one month |

## 0. Decisions made before we start

| Decision | Choice | Why |
|---|---|---|
| Reuse | Same stack, `tenantScope`, `recordAudit`, `withTransaction`, `requirePermission`, error catalog, `@shared`, dependency registries, `outbox_events`, `simplePdf`, counters, `PrivateStorage`, CSV helper, `studentService`, `employeeService`, `academicService` | Isolation, audit, permissions for free |

| Database | MongoDB stays (the PRD says PostgreSQL). We get the same safety from **transactions, unique indexes, conditional updates (`$inc` with a guard) and a `version` field** | One database for the whole app |
| Money | `…Paise` integer fields. Rates in **basis points** (`1800` = 18%). Rounding is "half up" per line, written in one helper `money.ts`. UI uses `formatMoney` and a `MoneyField` that takes rupees and sends paise | Never a float |
| Legal entity | **One per school** for now. Every finance row still stores `legalEntityId`, so more can be added later. Cross-entity transfers are later | Keeps the first release simple |
| Cost centre | The **Location** (Module 1). No separate cost-centre table | Zero re-entry |
| Who can do what | Still **four roles**. Finance work is given as **job bundles** (extra permissions given to a Staff user by the School Admin): Collector, Fee Manager, Accountant, Payroll Officer, Approver, Auditor (read only). Checked in the database on every request, so removing a bundle works at once | PRD: "capabilities, not new roles" |
| Posting engine | One function `postJournal()` is the **only** way to write journals. It checks balance, period, legal entity and a unique `sourceKey` (so the same event can never post twice). Journals have **no update or delete route and no update in code** | PRD §12, §87 |
| Posting rules | Written in code, one small file per event (`bill.issued`, `collection.posted`, …). Account choice comes from the fee head or a **system account role** on the chart of accounts (e.g. `STUDENT_RECEIVABLE`). Changing a mapping never edits old journals | Simple and testable |
| Accounting basis | Bills are booked as income when **issued** (accrual). Advances and deposits are **liabilities** until used. Deferred income is later | PRD §62, simplified |
| Student balance | Computed from `student_ledger_entries` (append-only rows written in the **same transaction** as each event, each linked to its bill and journal). Never stored as an editable total | PRD guardrail |
| Dates, not jobs | Overdue, PLANNED/ACTIVE/ENDED and "late fee due" are **worked out from dates** (school time zone). Late fees and billing are **buttons with a preview**, not nightly jobs | Same idea as Modules 2–5 |
| Numbers | Bill, receipt, journal and payslip numbers come from gap-free counters inside the same transaction: `RCT/2026-27/000123`. A cancelled number is never reused | PRD §33 |
| Tax | Tax codes are **settings** (exempt, nil-rated, out of scope, taxable with a rate). Seed values are **examples only** and every screen says "confirm with your accountant" | PRD App. B |
| Payroll rules | PF, ESI, Professional Tax and TDS live in **versioned rule packs**. Seed packs are **demo values**. The school's accountant enters the real ones before real use | PRD §48 |
| Private files | Proofs, bank statements, payslip PDFs and bank files use `PrivateStorage` and signed links (60 s) | No new storage code |
| DTOs | Explicit mappers per audience (`toBillDTO`, `toParentBillDTO`, `toPayslipDTO`, `toSalarySummaryDTO` …). No Mongoose document leaves a route. `shared/data-classification.ts` marks every money, bank and salary field. The existing classification test must fail if a field is missing or leaks | Same safety net |
| Other modules | They read finance **only** through `financeService` (`getStudentBalance`, `getStudentClearance`, `getFeeSummaryForParent`). They never keep their own fee totals | Like `spaceService` |

### Simplifications versus the PRD (on purpose)

| PRD item | What we do | Later |
|---|---|---|
| Accounting periods `OPEN → REVIEW → CLOSED → LOCKED` | `OPEN → CLOSED → LOCKED`. The **close-readiness check** does the job of REVIEW. Locked periods can't be reopened | Approved reopening of locked periods |
| Approval steps (many approvers) | **One approver** per request, who must be a different person from the requester (can be switched off per policy with a warning that is audited) | Multi-step chains |
| Revenue recognition schedules, budgets, petty cash, vendor advances, vendor credit notes | Not built. Income is booked when billed | P1 finance extension |
| Cash flow statement | Cash book and bank book instead | Cash flow |
| Sponsor-as-payer, RTE reimbursement, early-pay discount | Not built. A sponsor can be handled as a concession of type SPONSOR | Payer model |
| Fee precedence chain (override → programme → grade → school) | **One published plan per student per session.** A student override is a special plan for that student. Two matching plans = a conflict to review | Programme rules |
| Statutory engine | PF, ESI, Professional Tax slabs and a per-employee **monthly TDS amount** from a simple declaration. A full income-tax projection is later | TDS projection, LWF, gratuity calculator |
| Employee attendance | Monthly paid-days summary: manual entry or CSV. A missing summary is an exception, never "assume full month" | Attendance feed |
| Bank file formats | One generic CSV (name, account, IFSC, amount, reference). The file does **not** mark anyone paid | Bank-specific layouts |
| GST | Classification, calculation on bills and expenses, ITC register, output/ITC summary and return-ready CSVs. **No e-invoice, no e-way bill, no filing, no ITC reversal rules** (Rule 42/43 are flagged as "ask your accountant") | Filing connectors |
| Import | CSV only, one request, safe to retry (like Modules 4–5) | Excel, job queue |
| Domain events | Written to `outbox_events`. No broker | Message bus |
| MFA | Skipped, same as Modules 3–5 | MFA for finance users |
| Student-wise optional services (transport, hostel) | Optional fee items chosen on the student's fee assignment | Service module |

## Part 1: Finance foundation, fees, billing and tax basics (backend)

**Work packages:** FIN-01 to 08, 16 (basic), 19; FEE-01 to 14; TAX-01 to 03; FUX-01 (readiness data)

> Start of the part: re-read how `requirePermission`, the `/me` permission list, `simplePdf`, counters, `outbox_events` and the Module 4 hooks work today, then follow them. Build **foundation first** (items 4–15), because every later step posts a journal.

**Shared contract and permissions**
1. Enums, Zod schemas (`.strict()`), DTOs and error codes go in `backend/src/shared`. `data-classification.ts` gets every new field: bank numbers, salary, tax IDs and balances are classified; the classification test covers them.
2. New permissions (School Admin has all; Faculty, Staff and Parent get none by default). Finance: `finance:view`, `finance:setup:manage`, `finance:fee_plan:manage`, `finance:billing:create`, `finance:billing:approve`, `finance:concession:manage`, `finance:concession:approve`, `finance:adjustment:create`, `finance:adjustment:approve`, `finance:collection:record`, `finance:collection:verify`, `finance:receipt:cancel`, `finance:refund:request`, `finance:refund:approve`, `finance:refund:disburse`, `finance:reconciliation:manage`, `finance:cashier:shift`, `finance:cashier:supervise`, `finance:accounting:view`, `finance:accounting:post`, `finance:period:close`, `finance:expense:record`, `finance:expense:approve`, `finance:vendor:manage`, `finance:tax:manage`, `finance:tax:review`, `finance:report:view`, `finance:report:export`, `finance:audit:view`, `finance:access:manage`. Payroll: `payroll:setup:manage`, `payroll:structure:manage`, `payroll:input:manage`, `payroll:run:prepare`, `payroll:run:approve`, `payroll:disbursement:manage`, `payroll:disbursement:verify`, `payroll:salary:view_sensitive`, `payroll:settlement:manage`, `payroll:report:view`.
3. **Job bundles** in `shared/permissions.ts` (`FINANCE_BUNDLES`): *Collector* (record, shift), *Fee Manager* (plans, billing prepare, concession manage), *Accountant* (accounting, reconcile, expenses, tax, reports), *Payroll Officer* (all `payroll:*` except approve), *Approver* (all `…:approve`, `period:close`, `payroll:run:approve`), *Auditor* (view and audit only). Error codes (examples): `PERIOD_CLOSED`, `JOURNAL_UNBALANCED`, `SOURCE_ALREADY_POSTED`, `ACCOUNT_NOT_POSTABLE`, `PLAN_CONFLICT`, `PLAN_VERSION_FROZEN`, `TAX_CODE_MISSING`, `BILL_ALREADY_ISSUED`, `APPROVAL_REQUIRED`, `SELF_APPROVAL_BLOCKED`, `VERSION_CONFLICT`.

**Finance access (FIN-07)**
4. `GET/PUT /finance/access/users/:userId { bundles, locationIds? }` (`finance:access:manage`). Effective permissions = role matrix + the user's bundles, **read from the database each request** (no cache). `/me` returns the combined list so the UI `<Can>` works. Only a Staff user (or Admin) can hold bundles. Faculty cannot. A bundle never widens the user's **location scope**.

**Legal entity, years, periods, accounts (FIN-01 to 04)**
5. `GET/PATCH /finance/legal-entity` is created from the school profile with defaults (name, state from the primary location, FY starts in April). `gstin` is validated by shape. Changing tax identity writes audit.
6. `POST /finance/financial-years { code }` makes the year **and its 12 monthly periods**. `GET /finance/accounting-periods`. A normal user cannot change a `CLOSED` or `LOCKED` period (closing comes in Part 3, but the guard is built now inside `postJournal`).
7. `chart_of_accounts` is seeded with a school-ready chart (assets: bank, cash, student receivables, employee advances; liabilities: student advances, refundable deposits, salary payable, PF/ESI/PT/TDS payable, refund payable, vendor payable, output CGST/SGST/IGST; income: tuition, admission, annual, transport, exam, other; expenses: salaries, employer contributions, rent, utilities, maintenance, supplies, bank charges; input CGST/SGST/IGST; equity). Each key account gets a **systemRole** (`STUDENT_RECEIVABLE`, `STUDENT_ADVANCE`, `REFUNDABLE_DEPOSIT`, `SALARY_PAYABLE`, …). `POST/PATCH /finance/chart-of-accounts`: unique code, only leaf accounts are postable, an account with journal lines can be made inactive but not deleted, and a system role cannot be moved without approval.
8. `POST/GET/PATCH /finance/bank-accounts` and `/cash-accounts`: link to a GL account and locations. The number is **encrypted**, only `last4` is returned, and a full number needs `finance:setup:manage` plus a reason (audited, like Module 3 reveal). **Changing a bank account's number or IFSC needs an approval request.**

**Posting engine (FIN-05, 16, 19)**
9. `postJournal({ eventType, sourceKey, accountingDate, lines, memo, correlationId })` inside the caller's transaction. It rejects: lines that don't balance, a period that is not `OPEN`, an account that is inactive or not postable, a duplicate `sourceKey` (returns the **existing** journal when the retry is identical, so retries are safe). It gives the journal a number (`JV/2026-27/000045`) and writes an outbox event.
10. `reverseJournal(journalId, reason)` posts a mirror journal linked by `reversesId`. This is the **only** way to undo. The original is never touched. If the old period is closed, the reversal goes into the current open period with a note.
11. Immutability is enforced in code, not by habit: the Mongoose models for `journal_entries`, `journal_lines`, `fee_document_lines` (after issue), `finance_receipts` (content), `student_ledger_entries` and `employee_payslips` **throw on update and delete**. A test tries and fails.
12. Money helper `money.ts`: `toPaise(rupeesString)`, `formatMoney`, `splitEvenly`, `roundHalfUp`, `percentOf(paise, bps)`. Used everywhere. A lint check forbids `parseFloat` / `Number()` on money fields.
13. Read routes: `GET /finance/journals` (filters: date, account, student, source), `GET /finance/journals/:id` (lines + the source it came from), `GET /finance/general-ledger?accountId&from&to`, `GET /finance/trial-balance?asOf` (also tells you if debits ≠ credits, which must never happen).

**Approvals and audit (FIN-06, 08)**
14. `finance_approval_policies` are seeded: refund (any amount), credit note / waiver above ₹5,000 (editable), concession above its policy cap, payroll finalize (always), period close (always), bank-detail change (always), manual reconciliation override (always). `POST /finance/approvals` creates a request that stores **the proposed change, the money effect and the reason**. `POST /finance/approvals/:id/decide { approve|reject, reason }`. The decider must hold the permission and, by default, **must not be the requester** (`SELF_APPROVAL_BLOCKED`). An approval makes the action allowed once. The service then re-checks the data (it may have changed) before doing it.
15. `finance_audit_events` are written in the same transaction for every setup change, post, reverse, approval, export, bank-detail reveal and big read (bank number, salary). `GET /finance/audit` (`finance:audit:view`).

**Tax (TAX-01 to 03)**
16. `GET/PATCH /finance/tax-profile`: registered or not, GSTIN, state. `GET/POST/PATCH /finance/tax-codes`. Seed examples: *Exempt – educational service*, *Nil rated*, *Out of scope*, *GST 5%*, *GST 12%*, *GST 18%* (each with the note "Example only. Confirm with your accountant"). A used tax code can be ended, not deleted.
17. `calculateTax({ amountPaise, priceMode, rateBps, intraState })` is a **pure function**. Exclusive: tax = taxable × rate. Inclusive: taxable = amount ÷ (1 + rate). Intra-state splits into CGST + SGST (half each, the odd paisa goes to CGST), inter-state gives IGST. Student bills are always **intra-state** (the school's state). Discounts reduce the taxable value **before** tax. Every result carries a one-line explanation ("₹1,500 + 12% GST ₹180 = ₹1,680").
18. A fee head with no tax code cannot be billed. The billing row says `TAX_CODE_MISSING` and points to the fix. Credit notes copy the tax of the bill line they reduce (TAX-04 starts here).

**Fee configuration (FEE-01 to 04)**
19. `fee_heads`: `GET/POST/PATCH /finance/fee-heads`. Needs an income account and a tax code. A **refundable deposit** head must point to a liability account and is never income. Used heads can be inactivated, not deleted.
20. `fee_plans`: `POST /finance/fee-plans` and `POST /finance/fee-plans/:id/versions` (copy of the latest). Items hold amount, frequency, due day, grace days, proration method (`FULL_PERIOD`, `CALENDAR_DAYS`, `NONE`) and optional flag. `POST /finance/fee-plan-versions/:id/validate` returns plain-word problems: no items, head without account or tax code, dates outside the session, **another published plan covers the same students**. `…/approve` and `…/publish` (needs `finance:fee_plan:manage`; approve may need a second person by policy). **Published versions are frozen** (`PLAN_VERSION_FROZEN`). A price change = a new version with `effectiveFrom`. The older version becomes `SUPERSEDED` and old bills never change.
21. **Recommend and assign:** `POST /finance/fee-plan-assignments/recommend { sessionId, locationId, classId? }` looks at Module 4 enrollments and returns, per class, **"164 eligible · 157 ready · 7 need review"** with a reason for each exception (`NO_PLAN`, `PLAN_CONFLICT`, `ALREADY_ASSIGNED`, `NOT_ENROLLED`). `POST /finance/fee-plan-assignments/bulk` commits the ready ones in one request and returns done / skipped with a reason per student, and a **money preview** ("Expected this year: ₹41.2 lakh"). It is safe to retry. A plan with **auto-assign on** also assigns a new student when Module 4 makes an enrollment (through the Module 4 hook). When exactly one plan fits, it assigns by itself. Otherwise it creates a review row. Transfers and promotions end the old assignment on the right date and start a new one (FEE-15).
22. `PATCH /finance/students/:id/assignment` changes the optional items (e.g. add Transport). A student-only override is a plan with `appliesTo.studentId`. Both need a reason and are audited.

**Concessions, late fees, proration (FEE-05 to 08)**
23. Concession policies and awards: `GET/POST/PATCH /finance/concession-policies`, `POST /finance/concessions/recommend { studentId | classId }`, `POST /finance/concessions/award`, `POST /finance/concessions/:id/approve|reject|end`. **Recommend** finds **siblings** (another active student sharing a guardian, from Module 4 links) and **staff children** (a guardian whose person is also an active employee, same person record from Module 3). A policy says which heads it covers, whether it stacks or "highest wins", its cap (e.g. total discount ≤ 50% of a head), dates, and whether evidence or approval is needed. A concession never creates a payment. After issue, an approved concession creates a **credit note**, not an edit.
24. `late_fee_policies`: fixed or percent, per day, per month or once, grace days, cap. `POST /finance/late-fees/preview { asOf }` lists overdue bills and the late fee each would get (with the formula in words). `POST /finance/late-fees/commit` creates a `LATE_FEE` bill per item. Source key `latefee:<billId>:<periodKey>` means **the same late fee can never be made twice**. A waiver is a credit note with a reason, not a deleted fee.
25. **Proration** (joining or leaving mid-period): the billing engine applies the item's method and writes the formula into the line: "18 of 30 days × ₹4,000 = ₹2,400". A back-dated event on an already issued bill creates an **adjustment proposal** (`financial_adjustments` in `DRAFT`), never a silent edit.

**Billing (FEE-09, 10, 11)**
26. `POST /finance/billing-runs { sessionId, locationId, classIds?, periodKey, issueDate, dueDate? }` prepares a run. `POST …/validate` builds one row per student: **READY** or **NEEDS_ATTENTION** with a reason (`NO_PLAN`, `PLAN_CONFLICT`, `TAX_CODE_MISSING`, `STUDENT_NOT_ENROLLED`, `ALREADY_BILLED`, `PERIOD_CLOSED`, `AWARD_EXPIRED`). The response is the headline **"2,796 ready · 54 need attention"** plus the money total. `GET …/rows?status=` pages the exceptions. `PATCH …/rows/:id` can skip one row (reason) or fix it by calling the right API.
27. `POST …/commit` (needs `finance:billing:approve`, preview confirmed, `Idempotency-Key`): creates each student's bill **in its own transaction**: lines (price, concession, tax), `student_ledger_entries`, and the `bill.issued` journal (Dr Student Receivable, Cr Income + output GST, or Cr Refundable Deposit). The run has a **checkpoint**, so after a crash a retry continues and **never duplicates** (the line `sourceKey` = student + fee item + period). Bills snapshot the description, price, tax and plan version.
28. **Bill numbers** `BILL/2026-27/000231`. Bill status: `ISSUED → PARTIALLY_SETTLED → SETTLED` (or `CANCELLED` by credit note). **Overdue** is calculated (`dueDate + grace < today and balance > 0`). `GET /finance/fee-documents` (filters) and `GET /finance/fee-documents/:id` (lines, tax split, journal link, history). `GET …/pdf` makes a bill or **tax invoice** (shows GSTIN and tax split when any line is taxable; otherwise "Fee bill").
29. **Adjustments:** `POST /finance/fee-documents/:id/adjustments { type, lines, reason }` for credit note, debit note, waiver and late-fee reversal. It follows the approval policy (`APPROVAL_REQUIRED` with the request id). A credit note posts the mirror journal (Dr Income and output GST, Cr Student Receivable) and the ledger row. **It can never take a bill below what is already paid** (the extra becomes an advance). There is no route that sets a balance directly.

**Student account and explain (FEE-12 to 14)**
30. `GET /finance/students/:id/account` returns **separate labelled amounts**: billed, concession, tax, paid, outstanding, overdue, advance, and *expected later* (future instalments, shown apart and **never counted as owed**). `GET …/ledger` (timeline of entries, each with its bill and journal link). `GET …/upcoming`. `GET …/statement?from&to` (JSON and PDF).
31. `GET /finance/students/:id/balance-explanation` returns the lines of the sum in order: "Tuition ₹4,000 − Sibling concession ₹400 + Late fee ₹100 − Payment ₹3,700 = ₹0 left", each part linking to its bill, receipt or journal. The test proves the explanation total equals the account outstanding.
32. `GET /finance/outstanding?locationId&classId&bucket` gives aging (current, 1–30, 31–60, 61–90, 90+ days overdue) with totals by class, and a list. `GET /finance/families/:guardianId` gives the **family view** by adding up each linked child's own account, never a merged ledger. Access checks each child.

**Parent read access and other modules (FEE-15)**
33. `GET /parent/fees/summary` and `GET /parent/fees/students/:id` (bills, balance, how to pay, receipts later). Allowed only through an **active guardian link with the `FEES` capability** (Module 4), checked in the database each time. A parent never sees a sibling not linked, and no money field of staff-only data.
34. `finance/financeService.ts`: `getStudentBalance(studentId)`, `getStudentClearance(studentId)` (billed, paid, pending claims, refundable advances and deposits, `status: CLEAR | DUES | PENDING_CLAIMS`), `getFeeSummaryForParent(...)`. Module 4's TC "dues" check will read `getStudentClearance` (hooked up in Part 3, item 31). Register in the **dependency registry**: a student with bills cannot be hard-deleted; a location with bank accounts or journals cannot be archived; a Module 3 employee with payroll history keeps their record.
35. **Readiness:** `GET /finance/readiness` returns a checklist (legal entity, tax profile, financial year and periods, chart of accounts, bank account, fee heads with tax codes, a published fee plan, students assigned, approval policies) each as `DONE`, `NEEDS_ATTENTION` or `NOT_NEEDED`, with a plain sentence and a fix link. Part 3's items are added to this list later.
36. **Events** (to `outbox_events`, same transaction): `fee_plan.published`, `fee_assignment.created`, `fee_demand.issued`, `fee_demand.adjusted`, `journal.posted`, `journal.reversed`, `approval.decided`, `financial_year.created`.
37. **Isolation and audit:** all queries use `tenantScope` and **location scope**. A UUID from another tenant returns 404. A location the user cannot use returns 403 plus a `CROSS_SCOPE_DENIED` event. Every write audits in the same transaction.
38. **Seed (demo):** Greenfield legal entity (fake GSTIN `03AAAAA0000A1Z5`), State-bank demo account (`••••1234`), FY 2026-27 with 12 periods, the chart, tax codes, fee heads (Tuition, Annual, Computer, Examination, Transport, Security Deposit, plus a sample taxable *Uniform* head), the **Class VIII plan** (Tuition ₹4,000 monthly, Annual ₹8,000 yearly, Computer ₹1,500 quarterly, Exam ₹2,000 per term), a sibling concession policy (10% of tuition), a late-fee policy, an Accountant user (Staff with bundles) and an Approver. ## Part 3: Collections, banking, payroll, expenses, GST, close and reports (backend)

**Work packages:** COL-01 to 11; FIN-09 to 15, 17, 18, 20; PAY-01 to 15; TAX-04 to 09; FEE-15 to 17; FUX-03, 13, 15 (data)

> This is the biggest part. Build it in this order and keep `npm test` green after each block: **3A Collections → 3B Banking → 3C Payroll → 3D Expenses and GST → 3E Close, reports, attention.** The same `postJournal()` from Part 1 is used by all of them. No block writes its own accounting.

### 3A. Collections (COL-01 to 11)

1. **How money moves in the books (simple version):** receiving money first posts **Dr Bank/Cash, Cr Student Advance** (the school now holds the family's money). Allocating to a bill posts **Dr Student Advance, Cr Student Receivable**. Whatever is not allocated stays as an **advance (a liability)**, never income. Both journals are made in the same transaction, so a normal payment looks like one step to the user.
2. **Claims:** `POST /parent/payment-claims { students: [{studentId, amount}], method, amount, paidOn, reference, proof? }` (parent, linked child with `FEES`) and `POST /finance/payment-claims` (staff on behalf). A claim is `REPORTED → PENDING_VERIFICATION`. It **never** touches a bill or journal. Duplicate reference (normalised: upper-case, spaces removed) or same amount, same day, same student sets a `DUPLICATE_SUSPECTED` flag. `GET /finance/payment-claims/pending`. The parent sees **"Awaiting school verification"** until staff verify.
3. **Cash:** `POST /finance/collections { method: CASH, payer, studentAllocations[] | autoAllocate: oldest-first, amount }` needs an **open cashier shift** (`NO_OPEN_SHIFT` explains how to open one). It posts, allocates, issues the receipt and updates the shift in one transaction. Partial, multi-bill, multi-child and advance payments are all allowed. Retry with the same `Idempotency-Key` gives the same receipt.
4. **UPI / bank transfer:** `POST /finance/collections` with method `UPI|NEFT|RTGS|IMPS|BANK_DEPOSIT` makes a `PENDING_VERIFICATION` collection (from a claim or a staff entry). `POST /finance/payment-claims/:id/verify` and `POST /finance/collections/:id/verify { evidence: { statementLineId? | note, seenOn }, amountSeen }`. Verify checks: amount matches (else `AMOUNT_MISMATCH` and a choice), the **bank account is the school's**, the reference is not already used on another collection, and the statement line (if given) is not already matched. A UTR alone is a clue, not proof. Only after verify does posting, allocation and **receipt** happen. A **"Fast verify"** appears when an imported statement line matches exactly (Part 3B suggestion), still one click by a human.
5. **Cheques:** `POST /finance/collections` with cheque details (number, bank, date, payer) starts `RECEIVED` and gives a **provisional acknowledgement** (a different number series, clearly not a receipt). `POST /finance/collections/:id/deposit` (links a deposit batch), `…/clear` (clear date) and `…/return { reason, chargePaise? }`. Only **clear** posts the money and issues the final receipt. **Return** after clearing reverses the allocations (reversal + new, history kept), restores the bills, and may add a bank-charge debit note (needs approval).
6. **Allocation engine:** `POST /finance/collections/:id/allocate { items[] }` or `autoAllocate`. Rules: only `VERIFIED/POSTED/CLEARED` funds, never more than the bill balance or the unallocated amount, right student and entity, oldest due date first unless the payer chooses an order. **Concurrency:** each side uses a guarded update (`balancePaise >= x`, `unallocatedPaise >= x`) inside the transaction. If it fails, the whole allocation rolls back (`ALLOCATION_CONFLICT`). `POST /finance/collection-allocations/:id/reverse { reason }` posts the reversal and a replacement is a new allocation. History is never erased.
7. **Advances:** unallocated money stays on the student as an advance. `POST /finance/students/:id/apply-advance` applies it to open bills (also offered automatically when the next bill is issued, controlled by a setting). A family transfer of advance between siblings needs approval and a reason.
8. **Family payment:** `POST /finance/collections` accepts allocations to **several children of the same guardian**. Each child's access is checked. Example: ₹5,000 → Aarav ₹4,000 + Riya ₹1,000, Riya still owes ₹2,500. The receipt lists each child.
9. **Receipts:** made by the same transaction, numbered `RCT/2026-27/000123`, never reused. `GET /finance/receipts/:id`, `…/pdf`, `POST /finance/receipts/:id/cancel { reason }` (permission, approval for big amounts) makes a linked cancelled record and reverses the allocation. **A final receipt is never made for a pending claim** (test). Parent: `GET /parent/fees/receipts` and download for linked children only.
10. **Refunds (COL-10):** `POST /finance/refunds { studentId, reason, amount }` → system checks the **refundable amount** (advance + refundable deposit + overpaid credit, minus earlier refunds and open bills) and the recipient (a linked guardian) → `POST …/approve` (policy, different person) posts **Dr Student Advance (or Deposit), Cr Refund Payable** → `POST …/record-disbursement { bankAccountId, reference, paidOn, evidence }` (money really left) posts **Dr Refund Payable, Cr Bank**. A refund can never exceed what is refundable (`REFUND_EXCEEDS_CREDIT`). Cash refunds go through the shift.
11. **Cashier shifts and cashbook (FIN-12):** `POST /finance/cashier-shifts/open { openingFloat }`, `POST …/close { countedPaise }` gives expected vs counted and **variance** ("expected ₹48,500, counted ₹48,000, short ₹500"). A variance needs a note and a supervisor sign-off (`finance:cashier:supervise`). Past receipts are never edited to hide a shortage. `POST /finance/cash-deposits { shiftIds, bankAccountId, amount }` makes a deposit batch that a bank credit will match later. `GET /finance/cashbook?date`.
12. **Library of collection reports (COL-11):** collections by day, method, class, fee head and cashier · pending verification list · cheque register · advances list · refund register. JSON + CSV.
13. **Fee extras (FEE-15 to 17):** (a) `getStudentClearance` now feeds Module 4's TC: the dues check reads it; if it says `DUES` the TC stays `PENDING_CLEARANCE`; a manual clear still works but needs a reason (**check how `duesStatus` is set today and make the smallest change**). (b) Withdrawal gives a **clearance summary** (billed, paid, pending claims, refundable advance and deposit, open refunds). (c) Promotion hook: after Module 4 promotes, `recommend` assigns the new session plan and carries credits and unpaid amounts with the right period, **never billing the annual fee twice** (source key). (d) `POST /finance/fee-imports` CSV: opening student balances and fee assignments with preview, commit, safe retry. (e) `POST /finance/reminders/preview|send` makes a reminder list (overdue ≥ N days) and writes it to the notifier outbox (dev outbox as in Module 3). Reminders show the amount and bill numbers only.

### 3B. Banking and reconciliation (FIN-09 to 11)

14. **Statement import:** `POST /finance/bank-statements/import` (CSV; **auto-map columns** and remember the mapping per bank account). Checks: file belongs to that account, dates sane, and `opening + credits − debits = closing` when balances are given. Keeps the **original file** privately. A file already imported (hash) is refused with a link to the earlier import. Each line gets a fingerprint (date, amount, reference, description, balance + an occurrence number), so **two real payments of the same amount on the same day are both kept** and, if the order is unclear, flagged `DUPLICATE_SUSPECTED` for review rather than dropped. Reference is normalised.
15. **Matching engine:** `POST /finance/reconciliation/auto-match { bankAccountId, from, to }`. For credit lines it looks at collections (UPI, transfer, cheque deposits, cash-deposit batches). For debit lines it looks at refund disbursements, salary batches, vendor payments, expenses. Score: exact normalised reference + exact amount + same account = **HIGH**; amount + date window + payer name hint = **MEDIUM**; otherwise suggestions only. Supports **one-to-one, one-to-many** (a salary batch debit vs N payments) and **many-to-one** (a cash-deposit batch vs several shifts). **Only HIGH with a single candidate auto-confirms**, and only when the other side is already verified. Everything else is `SUGGESTED` for a person. A match that has an unverified claim offers "Verify and Match" as one human click.
16. `GET /finance/reconciliation/exceptions?bankAccountId` returns the headline (**"432 imported · 407 matched · 18 waiting for verification · 4 amount mismatches · 3 possible duplicates"**), grouped, with candidates, confidence and reasons. `POST /finance/reconciliation/matches/:id/confirm|reverse`, `POST …/manual-match`, `POST /finance/reconciliation/lines/:id/ignore { reason }` (needs approval: *manual reconciliation override*). **Timing differences** (cheque not yet cleared) are listed apart from **unexplained variance**.
17. **Direct postings from a bank line:** `POST /finance/reconciliation/lines/:id/record-bank-charge` and `…/record-interest` (journals with proper accounts, linked to the line).
18. `GET /finance/reconciliation/summary?bankAccountId&asOf` is the **bank reconciliation statement**: balance per books, items in books not in bank, items in bank not in books, and the difference (must be fully explained or shown as variance).

### 3C. Payroll (PAY-01 to 15)

19. **Setup:** `GET/PATCH /payroll/policy` (pay-day basis `CALENDAR_DAYS | FIXED_30 | WORKING_DAYS`, rounding, approval needed), monthly `payroll_periods` made on demand. A period is independent of GL periods. Posting needs the GL period to be `OPEN`.
20. **Components and structures:** `GET/POST/PATCH /payroll/components` (Basic, HRA, Allowance, Bonus, PF, Professional Tax, TDS, LOP, Loan Recovery, Employer PF, Employer ESI; each with type, calc rule, flags `pfWage/esiWage/prorate`, GL account). `POST /payroll/salary-structures` and `…/versions` (effective-dated, versioned, frozen when approved). Names like **Senior Faculty A** can be suggested for designations, but a person must approve the assignment.
21. **Employee salary:** `POST /payroll/employee-assignments { employeeId, structureVersionId, mode, overrides, effectiveFrom }`. Name, department, designation and location are **read from Module 3**, never typed again. `POST /payroll/employee-assignments/recommend` suggests structures for employees without one. **Modes:** `MONTHLY`, `DAILY`, `HOURLY` (daily/hourly need approved days/hours). **Revisions:** `POST /payroll/salary-revisions` (needs approval); a **back-dated** one creates **differential arrears** in the next run (never rewrites a finalised payslip). Future-dated ones are allowed.
22. **Monthly inputs:** `GET/PUT /payroll/inputs?month`, `POST /payroll/employee-inputs/import` (CSV: employee code, working days, paid leave, LOP days, hours, extras). Approved summary or manual approved entry. **A missing required input is a payroll exception**, never "assume full month".
23. **Statutory rule packs:** `GET/POST /payroll/statutory-rules`, `…/:id/approve`. Kinds: **PF** (rates, wage ceiling, which components count), **ESI** (limit and rates), **Professional Tax** (state slabs), **TDS** (the monthly amount from a simple declaration: regime + estimated yearly tax ÷ remaining months, entered or imported, with evidence). Rules are effective-dated. A run uses the rule version in force for its month. The seeded pack is **marked "Demo values — your accountant must replace these"** and a run on an unapproved pack shows a warning (`STATUTORY_RULE_UNAPPROVED`). Employer contributions are **separate** and never reduce net pay.
24. **Advances and loans:** `POST /payroll/advances` (request → approval → **actual payment recorded** through the disbursement flow), with an instalment plan. Each run recovers the instalment automatically (shown as its own line) and reduces `remainingPaise`. Early repayment, change of plan (approval) and exit treatment (balance goes to full-and-final) are supported. Advances are an **asset (receivable)**, kept apart from salary payable.
25. **Run and calculation:** `POST /payroll/runs { month, scope }` → `POST …/calculate`. For each active employee in scope (from Module 3, by dates): compensation + paid days or hours + approved extras + arrears − deductions − recoveries → net. Each line stores the **formula in words** ("Basic ₹30,000 × 26/30 paid days = ₹26,000"), the rule version and rounding. **Gross, deductions, employer cost and net are four separate totals.** A `calculate` can be repeated and gives the **same answer** until finalised (test). Result headline: **"November payroll · 86 employees · 82 ready · 4 need action"** with totals and **change versus last month**.
26. **Exceptions:** `GET /payroll/runs/:id/exceptions`: `MISSING_INPUT`, `NO_SALARY_ASSIGNED`, `PENDING_REVISION`, `BANK_UNVERIFIED`, `NEGATIVE_NET`, `ADVANCE_EXCEEDS_NET`, `JOINED_OR_EXITED_THIS_MONTH` (review), `RULE_UNAPPROVED`. Each has a fix hint and link. `PATCH /payroll/runs/:id/employees/:eid` can hold an employee out of this run (reason) or add a one-off line (reason, audited).
27. **Approve and finalise:** `POST …/approve` (`payroll:run:approve`, a **different person** from the preparer, default) then `POST …/finalize` in one transaction that **freezes the results**, posts the journals (**Dr Salary Expense and Employer Contribution Expense; Cr Salary Payable (net), PF/ESI/PT/TDS Payable, Employee Advances (recoveries), Employer Contribution Payable**), creates **payslips**, and sets payout status `UNPAID`. Two approvers finalising at once → one wins (`VERSION_CONFLICT`). After this, only a **correction run** or **supplementary run** (arrears, bonus) can change anything, and it posts its own journals linked to the original.
28. **Payslips:** `employee_payslips` are a frozen snapshot (school/entity, employee, department, components, gross, deductions, net, paid days, LOP, recoveries). `POST /payroll/runs/:id/publish-payslips` makes them visible to employees (a separate, deliberate step). `GET /payroll/employees/:id/payslips` needs `payroll:salary:view_sensitive`. PDF via `simplePdf`.
29. **Bank file and payment:** `POST /payroll/runs/:id/disbursement-batch { bankAccountId }` builds the batch (one item per employee with net payable) and `GET …/bank-file` downloads the generic CSV (account numbers read from Module 3 restricted data **on the server**, never sent to the screen, download audited, file hash stored). **Making the file does not mark anyone paid** (test). `POST /payroll/disbursements/:id/record { items: [{employeeId, status, reference, paidOn}], evidence }` records the real payment: partial, failed and returned items are allowed; a retry for a failed item is a new item and **cannot pay more than what is still payable**. Cash or cheque salary is allowed with a reason.
30. **Verify and reconcile:** `POST /payroll/disbursements/:id/verify` by a **second person** posts **Dr Salary Payable, Cr Bank** and moves the run's payout status `UNPAID → PARTIALLY_PAID → PAID`. A bank debit line (Part 3B) can match the batch (one-to-many) and offer "Verify" automatically. `GET /payroll/liabilities` shows unpaid salary and statutory payables with age.
31. **Full and final:** `POST /payroll/employees/:id/full-final` (when Module 3 has an exit date) prepares a `FULL_FINAL` run for one person: unpaid days, leave encashment (days × rate, entered), notice adjustment, arrears, bonus, gratuity (entered amount for now), statutory, and recovery of advance balances. Flow: Prepare → Review → Approve → Issue statement (PDF) → Payment through the same disbursement flow → Verify. The employee's login rules stay in Module 3. Their payroll history stays.
32. **Self-service (PAY-14):** `GET /me/payroll/summary`, `/me/payslips`, `/me/payslips/:id/pdf`, `/me/advances`, `POST /me/tax-declaration`. Identity comes from the session only. A supplied employee ID is ignored. Only published payslips are returned. Faculty and Staff **cannot** call any `/payroll/*` route without the permission.
33. **Payroll reports (PAY-15):** payroll register, bank advice, statutory summary (PF, ESI, PT, TDS payable vs paid), salary liability aging, cost by location and department. JSON + CSV (`payroll:report:view`, export audited, salary fields only for `payroll:salary:view_sensitive`).

### 3D. Expenses, vendors and GST (FIN-13, 14; TAX-04 to 09)

34. **Expenses:** `POST /finance/expenses { amount, categoryId, date, vendorId?, locationId, taxLines?, paymentMode: BANK|CASH|UNPAID, accountId?, evidence? }` (fast path: amount → category → date → vendor → receipt). The system fills entity, period and account from the category. Above the policy limit it waits for `…/approve`. When approved it posts **Dr Expense (+ eligible input GST), Cr Bank/Cash/Vendor Payable** and becomes immutable. A correction is a reversal + new entry.
35. **Vendors and bills:** `POST /finance/vendors` (bank detail changes need approval), `POST /finance/vendor-bills` (lines, tax, due date, approval), `POST /finance/vendor-payments { allocations[] }` (partial and multi-bill; the payment is **recorded** after the school pays through its bank). `GET /finance/payables/aging`. Vendor payable is a separate account from Student Receivable.
36. **Input tax and ITC (TAX-05, 06):** each expense or vendor-bill tax line has `itcStatus`: `ELIGIBLE` (posts to the Input GST accounts), `NOT_ELIGIBLE` (the tax is added to the expense cost) or `NEEDS_REVIEW` (the bill/expense **cannot be approved** until someone decides). The school's default is `NEEDS_REVIEW` because a school with mostly exempt income may not claim much input tax (note for the accountant; no Rule 42/43 maths). `POST /finance/tax/itc-review { lineIds, decision, reason }` (`finance:tax:review`). Vendor state vs school state decides CGST+SGST or IGST.
37. **Tax on credit notes and refunds (TAX-04):** every credit note reverses the tax of the line it reduces. Tests cover exempt, taxable and inclusive cases.
38. **GST payments (TAX-07):** `POST /finance/tax/payments { month, kind: PAY_LIABILITY | USE_ITC, amount, bankAccountId?, challanRef }`. PAY_LIABILITY posts **Dr Output GST Payable, Cr Bank**. USE_ITC posts **Dr Output GST Payable, Cr Input GST**. They are records of what the school did on the GST portal and bank. Nothing is filed from here.
39. **GST reports (TAX-08):** `GET /finance/tax/reports/:type?month`: `outward-summary` (by tax code and rate), `exempt-and-nil-summary`, `itc-register`, `liability-summary` (output − eligible input − paid), `hsn-summary`, plus CSVs in a return-ready layout titled **"Working copy — not a filed return"**. `GET /finance/tax/review-queue` (TAX-09): fee heads without tax code, ITC lines needing review, taxable bills missing GSTIN rules, and a month whose GST payable does not match the ledger.

### 3E. Close, reports, attention and hardening (FIN-15 to 20, FUX-03, 13, 15)

A back-dated post is never silently moved.

Computed live from the current data. Rows are filtered by what the user may see. Counts feed the sidebar badge. `GET /finance/overview` gives **Finance Pulse**: collections today, outstanding and overdue, payroll payable, monthly expenses, unreconciled bank and cash.

## Assumptions to confirm

1. One school per tenant and **one legal entity per school** (as before). Several entities and cross-entity transfers are later.
2. The database stays **MongoDB** with transactions. The PRD's PostgreSQL is not needed for the rules to hold.
3. Finance staff are **Staff users with job bundles** given by the School Admin. There is no fifth role. A school with one admin can turn "needs a different person" off per policy, and that choice is audited.
4. Seed tax codes and payroll rule values are **examples**. The school's accountant must set the real ones. Nothing is hard-coded as law.
5. Student bills are always **intra-state** (CGST + SGST). Inter-state is used only on purchases.
6. Bills are booked as income **when issued**. Deferred income, budgets and petty cash are later.
7. Employee **attendance** is a monthly summary (entered or imported). Module 8 (Student Attendance) is not used for payroll.
8. Salary payment, refunds, vendor payments and GST payments happen **outside** SchoolVerse (the school's own bank). SchoolVerse records them, needs proof and reconciles them.
9. Module 4's TC "dues" check will read finance clearance. The exact change depends on how `duesStatus` is set in the code today (to be checked at the start of Part 3).
10. Module 6 is skipped. If it later needs finance (for example transport fees), it will read and write only through `financeService` and fee heads.
